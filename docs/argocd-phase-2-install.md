# ArgoCD migration Phase 2: install runbook (staging)

Companion to Phase 2 of `argocd-migration-plan.md`. Terraform does the install; this runbook covers
what to expect from the TFC runs and how to verify the result and log in for the first time.
Nothing here changes the cluster except the TFC apply itself.

## 1. What the PR changes

- `terraform/modules/aws/argocd/`: one `helm_release.argocd` of the `argo-cd` chart (version pinned
  under Phase 0 "Versions" in the plan), namespace `argocd`, `wait = true`, `atomic = false`,
  `cleanup_on_fail = false`, `timeout = 900`. Dex, notifications and Redis HA off, the
  ApplicationSet controller scaled to zero, single replicas, `server.insecure=true`, explicit
  resource requests and memory limits. No IRSA, no Ingress. The admin password is generated by
  the module (`random_password`) and reaches the chart as its bcrypt hash through `set_sensitive`
  (section 4).
- Each env's `cluster-addons-layer/main.tf` gains `module "argocd"` behind
  `var.argocd_enabled` (default `false`). Only staging's `terraform.tfvars` sets it to `true`.
- The module is added to `cluster_addons_layer_module_directories` so a change under
  `terraform/modules/aws/argocd` queues a cluster-addons run, and to `.circleci/config.yml` for
  fmt and validate.

## 2. Expected TFC plans

| Workspace | Expected plan |
|---|---|
| `ac_app_staging_cluster_addons_layer` | 1 to add: `module.argocd[0].helm_release.argocd`. Auto-applies. |
| `ac_app_development_cluster_addons_layer` | 0 changes (`argocd_enabled` is false). |
| `ac_app_production_cluster_addons_layer` | 0 changes (`argocd_enabled` is false). |

Anything else in the plan (a change to `module.cluster_addons` or `module.main_rails_app`) is not
this PR and must be understood before merging.

The staging apply runs `helm install` with `wait = true`, so it blocks until all ArgoCD pods are
ready, up to 15 minutes. If it fails, the release stays on the cluster for inspection
(`atomic = false`); fix the cause and re-queue the run. Do not `helm uninstall` by hand unless the
release is being abandoned: Terraform state would then point at a release that no longer exists.

```bash
kubectl -n argocd get pods
```

Expected: four Running pods (`argocd-application-controller-0`, `argocd-repo-server-*`,
`argocd-server-*`, `argocd-redis-*`) plus a Completed `argocd-redis-secret-init-*` Job pod from the
install. No dex, notifications or applicationset pods. The ApplicationSet Deployment exists with 0


Pod headroom after the install (the Phase 0 check, re-run):

```bash

```

## 4. Admin password and first login

Terraform generates the admin password. The `argocd` module holds a `random_password` and passes
its `bcrypt_hash` to the chart through `set_sensitive`
(`configs.secret.argocdServerAdminPassword`), together with the time the password was generated
(`configs.secret.argocdServerAdminPasswordMtime`, a `time_static`). There is nothing to set by hand
before enabling ArgoCD in an environment: the first install already carries the password and the
chart never creates `argocd-initial-admin-secret`.

Where the values live:

| Value | Where | Who can read it |
|---|---|---|
| bcrypt hash and mtime | `argocd-secret` in the cluster, and the workspace state | cluster-admin, TFC workspace readers |
| plaintext password | the `ac_app_<env>_cluster_addons_layer` workspace state only (output `argocd_admin_password`, sensitive) | TFC users who can read that workspace's state and outputs |

The plaintext is in Terraform state on purpose, like the database password and the Rails secret key
base that `main_rails_app` generates the same way. It is not in git, not in `terraform.tfvars`, and
plan output redacts it.

Why `random_password.bcrypt_hash` and not `bcrypt()` in HCL: the function salts differently on
every call, so it would upgrade ArgoCD on every run; the resource computes the hash once and reads
it from state afterwards. Why the mtime is a resource: the chart otherwise stamps the render time,
and every later `helm upgrade` would log every session out.

### 4.1 Read the password

Read it with the Terraform CLI. The workspace's **Outputs** tab in the Terraform Cloud UI lists
`argocd_admin_password` but masks it and has no control to reveal a sensitive value (seen on
staging, 2026-11-19); it does show `argocd_admin_password_mtime`, the time the password was
generated.

From `terraform/env/<env>/aws/us-west-1/cluster-addons-layer`, with a Terraform Cloud credential
(`terraform login` stores a user token through the browser; an exported `TFE_TOKEN` also works):

```bash
terraform login                                        # once per laptop; skip if TFE_TOKEN is set
terraform init
terraform output -raw argocd_admin_password | pbcopy   # to the clipboard, not the terminal
```

The account needs read access to the workspace's state outputs. Do not paste the password into a
chat, a ticket or a PR.

Last resort, if the CLI is not available: the workspace's **States** tab, latest state, JSON view,
search for `argocd_admin_password`. That view also shows every other secret in the state (database
password, Rails secret key base), so close it afterwards.

Copying it into the team password manager is optional; the workspace output is the source of
truth, and a copy goes stale at the next rotation.

### 4.2 First login

The server listens on plain HTTP (`server.insecure=true`) and has no Ingress, so both the CLI and
the UI go through a port-forward under the read-write `ac_ci_terraform_<env>` role.

**CLI.** Use the `argocd` CLI's own port-forward, with no `kubectl port-forward` running:

```bash
kubectl -n argocd get secret argocd-initial-admin-secret   # must return NotFound: Terraform set the password
export ARGOCD_OPTS='--port-forward --port-forward-namespace argocd --plaintext'
argocd version                   # needs no login; server v3.5.6
argocd login --username admin    # password from section 4.1
argocd app list                  # empty until Phase 5
```

Do not point the CLI at a `kubectl port-forward` (`argocd login localhost:8080 ...`). Seen on staging
on 2026-11-19 with CLI v3.6.1 and server v3.5.6: the forward exits with `read: connection reset by
peer` / `lost connection to pod` on the CLI's first connection and the CLI then reports `connection
refused`, with or without `--grpc-web`. The CLI opens a connection and closes it without sending
anything before its first request, which is the likely trigger.

**UI.** A browser is fine through `kubectl port-forward`:

```bash
kubectl -n argocd port-forward svc/argocd-server 8080:80
```

Then open `http://localhost:8080` and sign in as `admin`.

The port-forward path already requires the cluster-admin SSO role, so the password is the second
gate, not the first (see the "ArgoCD admin login" and "ArgoCD UI access" rows in the plan's
Decisions table).

### 4.3 Rotation

Set `argocd_admin_password_rotation` in the environment's `cluster-addons-layer/terraform.tfvars`
to a new value (the date works, for example `"2026-12-01"`; the default is `"1"`) through a PR.
The plan shows `random_password.argocd_admin` and `time_static.argocd_admin_password` replaced and
one in-place change to `helm_release.argocd` (production: fresh run, confirm promptly). The new
mtime invalidates every existing session; read the new password as in 4.1. Do not use
`argocd account update-password`: the next Terraform run would put the Terraform-managed hash
back.

### 4.4 An install that predates the generated password

Staging was installed on 2026-11-19 (#380) before the module generated the password, so the chart
created `argocd-initial-admin-secret` with a random one. The first apply of the generated password
shows 2 to add (`random_password`, `time_static`) and 1 to change (`helm_release.argocd`), after
which the bootstrap Secret is stale and the admin password is the one from 4.1. Delete the
leftover once that run has applied:

```bash
kubectl -n argocd delete secret argocd-initial-admin-secret
```

Phase 8 enables ArgoCD on production with the generated password from the first install, so this
step does not repeat there.

## 5. Rollback

Set `argocd_enabled = false` in staging's `terraform.tfvars` through a PR. Terraform destroys the
release and, with it, the `argocd` namespace. The chart keeps its CRDs on uninstall
(`crds.keep: true`); they are harmless and will be reused by a reinstall. Nothing in the
`automation-calculator` namespace is touched: ArgoCD has no Applications yet.

## 6. Done when

- Staging TFC run applied with exactly 1 resource added; development and production planned 0.
- `kubectl -n argocd get pods` shows the four pods Running.
- `argocd login` succeeds through the port-forward and `argocd app list` is empty.
- The admin password is the Terraform-generated one (workspace output `argocd_admin_password`) and
  `argocd-initial-admin-secret` does not exist in the `argocd` namespace.
- `scripts/argocd_preflight.sh` still exits 0 on staging (headroom for the Phase 3 canary pods).

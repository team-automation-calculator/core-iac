# GitHub CI Machine User

The organization has one machine user, `automation-calculations-ci-production`,
for deploy automation: the Terraform Cloud VCS connection, CircleCI, and the
`gh`-driven image-bump PRs in this repo. It exists so that none of those run on
a human's personal account and personal token.

Everything about the account *inside the organization* is Terraform-managed:
org membership, the `ac-ci` team, and the team's repository permissions
(`terraform/modules/github/org-ci-access`, applied from
`terraform/env/production/github/org` in the `ac_app_production_github_org`
TFC workspace).

The account *itself* is not. GitHub has no API for creating user accounts, and
its Terms of Service forbid accounts registered by bots or other automated
methods. One hand-made machine user for deploy scripts is explicitly allowed.
So account creation is a one-time manual runbook, below.

## 1. Create the account (once, by hand)

1. Confirm the login is still free: `gh api users/automation-calculations-ci-production`
   must return 404.
2. In a private browser window, go to <https://github.com/signup>.
   - Email: the `ci@` mailbox on the `automation-calculations.net` Google
     Workspace domain.
   - Username: `automation-calculations-ci-production`
   - Password: generated by the team password manager and stored there.
3. Verify the address from the `ci@` mailbox.
4. Settings → Profile: display name `Automation Calculations CI (production)`.
5. Settings → Password and authentication: enable two-factor authentication
   with a TOTP app. Store the TOTP secret and the recovery codes in the password
   manager next to the password.
6. Create nothing else: no repositories, no SSH keys, no tokens yet.

## 2. Invite it to the organization (Terraform)

The `ac_app_production_github_org` TFC workspace runs
`terraform/env/production/github/org`. Its plan creates:

- `github_membership.ci` — a pending invitation with role `member`
- `github_team.ci` — the `ac-ci` team
- `github_team_membership.ci`
- one `github_team_repository.ci[...]` per entry in `repository_permissions`

Apply it, then, logged in as the machine user, accept the invitation from the
email sent to the `ci@` mailbox (or at
<https://github.com/orgs/team-automation-calculator/invitation>). Invitations
expire after 7 days; if one lapses, re-running the plan recreates it.

The machine user is always a plain member, never an owner.

> Note: the organization's default repository permission is currently `write`,
> so every member, including this one, already has write on every repository on
> joining. The team grants document intent and become the real boundary once the
> org default is tightened to `read` (follow-up; not in this layer yet).

## 3. The owner token the workspace uses

Inviting members and managing teams requires an **organization owner's** token;
the machine user cannot manage its own access. The workspace therefore uses a
fine-grained personal access token created by an owner:

- Settings → Developer settings → Fine-grained tokens → Generate new token
- Resource owner: `team-automation-calculator`
- Expiration: 1 year (the maximum)
- Repository access: only select repositories, every repository listed in
  `repository_permissions` (today: `automation-calculator`, `core-iac`)
- Repository permissions: Administration **read and write**, Metadata read
- Organization permissions: Members **read and write**

Store it only as a **sensitive environment variable** named `GITHUB_TOKEN` on
the `ac_app_production_github_org` TFC workspace, with the expiry date in the
variable description. Never set it locally, never commit it, and do not reuse
the `TF_VAR_GITHUB_TOKEN` variable set: that token is repo-scoped for the
`tfe_oauth_client` and lacks the Members permission.

When a repository is added to `repository_permissions`, add it to the token's
selected repositories as well, or the `github_team_repository` apply fails.

## 4. Tokens for the machine user

Create a token only when a consumer needs one, and give each consumer its own:

| Consumer | Token type | Repositories | Permissions |
|----------|-----------|--------------|-------------|
| CircleCI image-bump PR job (`scripts/bump_app_docker_image_version_branch.sh`) | fine-grained | `core-iac` | Contents RW, Pull requests RW |
| Replacement for `TF_VAR_GITHUB_TOKEN` in the `tfe_oauth_client`s | fine-grained | `core-iac` | Contents R, Commit statuses RW, Webhooks RW; requires the `ac-ci` team's `core-iac` permission raised to `admin` first |

Rules:

- Fine-grained tokens only, 1-year maximum expiry, scoped to the fewest
  repositories and permissions that work.
- A token lives only in its consumer (a TFC variable, a CircleCI context). It
  is never stored locally and never shared between consumers.
- No classic PATs, no `admin:org`, no SSH keys for interactive use.
- Nobody uses the machine user interactively beyond this runbook.

## 5. Verify

```bash
gh api orgs/team-automation-calculator/members --jq '.[].login'
gh api orgs/team-automation-calculator/teams/ac-ci/memberships/automation-calculations-ci-production --jq .state
gh api orgs/team-automation-calculator/teams/ac-ci/repos --jq '.[] | .name + " " + (.permissions|tostring)'
```

The first lists the machine user, the second returns `active`, and the third
matches `repository_permissions` in the env tfvars. A fresh TFC plan on
`ac_app_production_github_org` shows no changes.
